GitHub Actions 锁文件实用教程：固定依赖并在 CI 中检查

2026-10-15 GitHub与开源 JIA
适用范围

本文按 GitHub 官方文档与 gh-actions-lock 仓库说明整理，核对时间为 2026-10-15。工作流依赖锁文件仍处公开预览阶段；仓库工具也处于 1.0 前开发期，命令细节可能变化。GitHub Enterprise Server 当前不受该扩展支持。

GitHub Actions 常见写法是 uses: actions/checkout@v4。标签便于升级，但团队需要知道运行时实际落到哪个提交。锁文件把工作流依赖对应到已核验的提交，并让 CI 可以检查锁文件是否跟工作流一致。

第一步：先检查工作流

在仓库根目录查看 .github/workflows/ 下所有 YAML 文件，确认每条 uses: 指向你认可的 action 版本。可复用工作流也要检查；它们的依赖由定义该可复用工作流的仓库管理。若组织启用了 Actions 允许列表，先确认锁定后的提交 SHA 也能通过策略。

建议先启用 Dependabot 的 GitHub Actions 更新，再接入锁文件。这样后续 action 升级可以和锁文件一起进入拉取请求，避免手动升级工作流却忘记更新锁。

--verify 只检查，不写文件；官方扩展仓库建议在 CI 使用它。--verify-local 只核对每个引用是否有锁条目，不验证锁定提交仍对应可信上游，因此不能代替在线的 --verify。实际 CI 工作流还需安装 GitHub CLI 和该扩展，再执行同一条检查命令。

后续维护与常见卡点

新增工作流，或增删现有工作流中的 uses: 后，重新运行 gh actions-lock 并提交工作流与锁文件。普通运行不会默默追随分支或短版本标签的新提交；如果上游标签移动，先去上游仓库历史核实原因，再考虑 gh actions-lock --relock。只有确认上游变更可信、且原提交已无法使用时，才考虑 --accept-moved，不要把它当成日常更新快捷键。

本地 uses: ./... action 如果无法解析，先检查路径是否相对仓库根目录、目标目录里是否有真实的 action 文件。官方文档说明扩展可能跳过无法解析的本地 action；看到跳过提示时应先处理，不要把“命令退出成功”当成所有依赖都已经锁好。

记住这条边界

锁文件提升依赖版本可复现性，但不替你判断锁定代码是否安全。每次提交都要审查 diff；公开预览期间也要留意官方文档与扩展 README 的变化。
